03 · Part 1A · Deterministic application

Part 1A: Tiered Rate Limiter

A deterministic rate-limiting component: the same sequence of requests always produces the same accept or reject decisions. Each client ID gets its own token bucket, sized by its subscription tier.

Problem statement

A backend API must stop any single client from overwhelming it, while giving higher subscription tiers more capacity. Part 1A implements this as a Python component using the Token Bucket algorithm, with a separate in-memory bucket for every client ID.

Intended behaviour

  • A request arrives with a client ID and a subscription tier.
  • If the client's bucket holds a token, one token is used and the request is accepted.
  • Tokens refill continuously at the tier's rate, up to the bucket's capacity.
  • If the bucket is empty, the component raises HTTP 429 Too Many Requests with a Retry-After header.
  • Different client IDs never share a bucket.

How the token bucket works

Picture a bucket of tokens for each client. Every request takes one token, and tokens drip back in at a fixed rate. A full Free bucket holds 5 tokens and refills at 5 per minute, so a client can send 5 requests at once and then gets one more token about every 12 seconds.

Inputs and outputs

Accepted

Rejected
Part 1A raises HTTPException(429) with Retry-After: the smallest whole number of seconds after which a retry is accepted.

Acceptance criteria

  • AC1 Requests within the limit are accepted.
  • AC2 Requests over the limit are rejected with HTTP 429.
  • AC3 The 429 carries Retry-After equal to the smallest sufficient wait (clarified 2026-11-07).
  • AC4 Limits are isolated per client ID.

Known limitations

  • Buckets live in process memory, so they are lost when the server restarts.
  • Separate worker processes or replicas do not share buckets; production use would need a shared store such as Redis.
  • A client's tier is fixed by its first request. Later requests with a different tier still use the first tier's bucket.
  • Inside Part 1A an unknown tier falls back to Free. This portal rejects unknown tiers before they reach Part 1A.
  • Part 1A is a Python component, not a deployed HTTP service; this portal adds the HTTP layer for demonstration.

Harness results

The Part 1A harness runs three gates: Ruff (lint), Bandit (static security analysis) and Pytest (unit and acceptance-criteria tests). It is run from a terminal with Part-1A/.harness/run.ps1, which saves every run. This page only displays those saved runs; it never executes the harness.

04 · Part 1B · Non-deterministic AI application

Part 1B: AI Security Code Reviewer

An AI-assisted security reviewer: you paste source code, Google Gemini analyses it, and the application returns structured findings. Because the model is non-deterministic, the wording (and sometimes the findings) can change between requests.

Problem statement

Manual security review is slow and inconsistent. Part 1B sends a code snippet to a Gemini model and asks for security findings in a fixed JSON structure, so that software can validate the answer even though the model's wording varies.

How Gemini is used

Model
gemini-3.5-flash-lite (configurable with GEMINI_MODEL)
SDK
Google Gen AI Python SDK, google-genai
Output
JSON constrained by a response schema, temperature 0.1, then validated locally
Credential
GEMINI_API_KEY, read only by the server; it never reaches this page

Why the output is non-deterministic

A language model generates text by sampling. Two requests with the same code can produce different wording, a different category name ("Remote Code Execution" instead of "Code Injection") or occasionally a different set of findings. Exact text matching is therefore the wrong test. Part 1B checks structure, rules that must always hold and category-level meaning instead.

Safety and guardrails

  • Submitted code is untrusted data: never executed, imported or stored by the portal.
  • The reviewer's prompt tells Gemini to ignore instructions embedded in the code and to report prompt-injection attempts.
  • Evidence must be an exact excerpt of the submitted code; Layer 2 checks this.
  • At most ten findings; severity limited to High, Medium or Low.
  • Model output is displayed as plain text. HTML inside findings is never rendered.
  • Service failures (quota, outage, timeout) are shown as errors, never as "no vulnerabilities".

Known limitations

  • Results depend on Gemini's availability, quota and network access.
  • Findings can vary between requests, so one result is not a stable verdict.
  • "No findings" does not prove code is secure; findings are suggestions for a person to review.
  • The 16-case evaluation dataset cannot cover every vulnerability type or language.
  • Layer 3 compares vulnerability categories using configured aliases; it is not an independent LLM judge.

05 · Part 1B evaluation evidence

Evaluation Dashboard

How Part 1B's non-deterministic output is judged: a fixed evaluation dataset, three validation layers, and an aggregate score compared with a threshold declared before evaluation. Everything on this page is read from saved report files; no model is called here.

How each case is scored

  1. Dataset case
  2. Live Gemini call
  3. Layer 1 · Schema
  4. Layer 2 · Invariants
  5. Layer 3 · Category match
  6. Aggregate score
  7. PASS or FAIL against 80%

Layer 1 · Structure

Valid JSON that matches the schema: required fields present, strings non-empty, severity one of High, Medium or Low.

Layer 2 · Invariants

Rules that must always hold: the status matches the case's expected status, an error response has no findings, at most ten findings, and every evidence value is an exact excerpt of the input.

Layer 3 · Semantic

The reported vulnerability category must match the case's expected category, allowing configured aliases ("Remote Code Execution" counts as "Code Injection"). Cases that expect "None" must have no findings. This is deterministic category/alias matching, not an LLM judge.

A case passes only when all three layers pass. Score = passed cases ÷ completed cases × 100. A run is PASS only when every case completed and the score is at least the declared threshold of 80%. A Gemini service error stops the run as INCOMPLETE, with no final score, so outages are never counted as application failures.
